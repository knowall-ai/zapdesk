= ZapDesk Email Channel Setup
:toc: left
:toclevels: 3
:icons: font

== Overview

ZapDesk turns inbound email into Azure DevOps work items and emails the
requester back when an agent replies or the ticket status, title or priority
changes.

* *Inbound*: a scheduler outside the app (a Logic App, see
  <<Scheduling the Poll>>) calls ZapDesk once a minute; ZapDesk polls the
  support mailbox via Microsoft Graph, ingests each unread message, then
  marks it as read.
* *Outbound*: confirmations, agent replies, status-change notifications and
  title/priority update notifications go out via Microsoft Graph `sendMail`
  from the same support mailbox.

----
Customer ──email──> support@yourdomain.com (Exchange Online)
                         ↑
                         │  Graph poll every minute
                         │
ZapDesk /api/email/poll ─┘
       │
       ├─ subject contains [ZapDesk #N]?
       │     yes → add comment to ticket #N
       │     no  → create ticket; route to project by sender domain
       │
       └─ Graph sendMail → Customer (confirmation / reply)
----

== Azure AD App for Mail

Create or reuse one Azure AD app with these *Application* permissions:

[cols="1,2"]
|===
|Permission |Why

|`Mail.Send`
|Outbound — confirmations, agent replies, status and title/priority updates

|`Mail.ReadWrite`
|Inbound — list unread mail and flag-as-read after processing
|===

[IMPORTANT]
====
Click *Grant admin consent* after adding the permissions. Without consent the
client-credentials token request will succeed but every Graph call will return
403.
====

=== Restrict to a single mailbox

`Mail.Send` and `Mail.ReadWrite` Application give the app access to *every*
mailbox in the tenant. Restrict it to the support mailbox only via an
{empty}https://learn.microsoft.com/graph/auth-limit-mailbox-access[Application
Access Policy^]:

[source,powershell]
----
Connect-ExchangeOnline

# Replace <APP_ID> with the Azure AD client ID of the mail app
New-ApplicationAccessPolicy `
  -AppId <APP_ID> `
  -PolicyScopeGroupId support@yourdomain.com `
  -AccessRight RestrictAccess `
  -Description "ZapDesk inbound + outbound — restricted to support mailbox"

# Verify
Test-ApplicationAccessPolicy -Identity support@yourdomain.com -AppId <APP_ID>
# Expected: AccessCheckResult = Granted
----

To cover multiple mailboxes later, create a mail-enabled security group
containing them and pass the group address as `-PolicyScopeGroupId`.

== Environment Variables

[source,env]
----
# Auth for the poll + webhook endpoints
EMAIL_WEBHOOK_SECRET=<random ≥32 chars>

# Mailbox ZapDesk polls for inbound mail
MAIL_POLL_MAILBOX=support@yourdomain.com

# Outbound sender (usually the same mailbox)
MAIL_FROM=support@yourdomain.com
MAIL_FROM_NAME=ZapDesk Support

# Dedicated mail app credentials
MAIL_TENANT_ID=<tenant id>
MAIL_CLIENT_ID=<app id>
MAIL_CLIENT_SECRET=<client secret>

# Service account PAT used to create work items (already required for ZapDesk)
AZURE_DEVOPS_PAT=<pat with Work Items Read & Write>
----

If the dedicated mail credentials are not set, ZapDesk falls back to the main
`AZURE_AD_*` app — but the main app should not have `Mail.*` permissions in
production, so configure the dedicated ones.

== Project Routing by Sender Domain

When a new message arrives, ZapDesk extracts the sender's email domain and
looks for an Azure DevOps project whose description contains that domain. The
ticket is created in the matched project.

To route mail from `acme.com` to a project, add the domain to that project's
description in Azure DevOps:

----
Customer support project for Acme. Email: acme.com
----

Multiple domains can be listed comma-separated. The mapping is cached for
~5 minutes; descriptions can be edited at any time.

== Scheduling the Poll

Something outside the app has to call `POST /api/email/poll` once a minute.
The repository holds two ways of doing that, but the live KnowAll AI
deployment uses neither: it runs a Logic App, which is the supported and
recommended poller.

[cols="2,2,3",options="header"]
|===
|Poller |Status |Notes

|*Logic App* (no code in this repo)
|Supported; what production runs
|One-minute Recurrence trigger and one HTTP action. Run history shows each
call and its status code. Set up below.

|*Azure Functions timer* (`azure/email-poll/`)
|Optional alternative; not deployed
|Built and tested in CI. Brings an Application Insights alert the Logic App
lacks. See its README for settings and cutover.

|*GitHub Actions workflow* (`.github/workflows/email-poll.yml`)
|Fallback; disabled
|The original poller. GitHub's schedule floor is five minutes and scheduled
workflows stop after 60 days without repository activity.
|===

=== The Poll Contract

Every poller, whatever runs it, makes the same call:

----
POST https://zapdesk.yourdomain.com/api/email/poll
x-webhook-secret: <EMAIL_WEBHOOK_SECRET>
----

* No body is needed. The header value must equal the app's
  `EMAIL_WEBHOOK_SECRET` exactly.
* Use the custom domain, never the `*.azurewebsites.net` hostname: the App
  Service only accepts traffic through Front Door (see `SETUP.adoc`).
* Allow up to 90 seconds for a response. A poll works through every unread
  message before it answers.
* `200` returns a summary: `mailbox`, `fetched`, `ingested`, `failed` and a
  per-message `results` list. A non-zero `failed` still comes back as `200`,
  so read the body, not just the status.
* `401 Invalid webhook secret`: the header is missing or wrong.
* `500 MAIL_POLL_MAILBOX not configured`, or `500` with an `error` message
  when Graph or Azure DevOps fails.
* `GET /api/email/poll` needs no secret and polls nothing. It reports whether
  the mailbox and secret are configured, so use it to check settings.

=== Setting Up the Logic App

. In the Azure portal, create a *Logic App* on the *Consumption* plan.
. Add a *Recurrence* trigger: interval `1`, frequency `Minute`.
. Add an *HTTP* action: method `POST`, URI
  `https://zapdesk.yourdomain.com/api/email/poll`, and a header
  `x-webhook-secret` holding the app's `EMAIL_WEBHOOK_SECRET`. Prefer reading
  the secret from Key Vault over pasting it in, and turn on *Secure inputs* in
  the action's settings so it stays out of run history.
. Give the HTTP action a timeout of at least 90 seconds.
. In the trigger's settings, turn on *Concurrency control* with a degree of
  parallelism of `1`, so a slow poll is never overlapped by the next tick.
. Save, then open *Run history*: each run should show the HTTP action
  returning `200`.

The Logic App raises no alert on its own. Add an Azure Monitor alert on
failed runs: a mailbox that has stopped being drained looks exactly like a
mailbox with nothing in it.

=== Run Exactly One Poller

Whichever you pick, *run exactly one*. Each poll lists unread messages and
only then marks them read, and the endpoint has no concurrency guard, so two
pollers can file the same email twice.

Hand over with a gap, never an overlap. Turning the old poller off does not
stop the run already in flight -- a disabled GitHub Actions schedule lets a
started job finish, and a poll can take up to 90 seconds -- so disable the
old one, wait for its current run to report finished, and only then enable
the new one. Unread mail simply waits for the next poll, so the gap costs
nothing; the overlap costs duplicate tickets.

== Email Threading

Subject prefix is the source of truth: every outbound email from ZapDesk
contains `[ZapDesk #<id>]`, and inbound mail with that prefix is appended to
the existing ticket as a comment instead of creating a new one. This works
across every email client, no custom Message-ID handling required.

Update notifications keep the subject of the ticket's original title, even
after the title is changed, so they stay in the customer's existing thread.
The new title is shown in the email's list of changes.

== Customer Emails

* Emails to the customer (confirmation, agent reply, status change, title or
  priority update) contain no links to ZapDesk: customers have no ZapDesk
  account. They are asked to reply to the email instead.
* Emails to the support team (new ticket, assignment, new customer reply) keep
  their *View Ticket* link.
* As soon as a ticket arrives by email, everyone in `SUPPORT_TEAM_NOTIFY_EMAIL`
  gets a "New ticket" email with the subject, sender, project and message. The
  setting takes one address (a group or distribution list) or several,
  separated by commas or semicolons. The polled mailbox and the customer who
  raised the ticket are always left out. If a team list includes the support mailbox, ZapDesk
  ignores its own email when it comes back in (anything sent from `MAIL_FROM`
  or the polled mailbox), so it is never filed as a customer reply.
* The "Earlier in this conversation" history quoted under an agent reply leaves
  out the customer's own replies, which they already have in their Sent folder.
* No "new customer reply" alert is sent when the ticket is assigned to the
  customer's own address.
* A customer's reply is stored as just their new message. The earlier ZapDesk
  email their mail client quotes underneath (Gmail's "On … wrote:" block,
  Outlook's "From: … Sent:" header, or `>` lines) is cut. A quote of anything
  else, such as a supplier's message, is kept.

== Security

* Webhook + poll endpoints authenticated with a shared secret (`x-webhook-secret`)
* Sender domain validated against project mappings — unknown domains rejected
* Internal notes (`[Internal Note] ...`) are never emailed to the customer
* Mail app scope restricted to one mailbox via Application Access Policy

== Troubleshooting

[cols="1,2"]
|===
|Issue |Solution

|Poll returns `401 Invalid webhook secret`
|`EMAIL_WEBHOOK_SECRET` mismatch between the GitHub secret and App Service.

|Poll returns `MAIL_POLL_MAILBOX not configured`
|Set the `MAIL_POLL_MAILBOX` env var on App Service and restart.

|Graph returns 403 on list / sendMail
|`Mail.ReadWrite` / `Mail.Send` not granted with admin consent on the mail app, or the Application Access Policy is excluding the mailbox.

|Emails create tickets in the wrong project
|Project description missing or contains the wrong domain. Edit the description in DevOps; the cache refreshes within ~5 minutes.

|Replies create new tickets instead of comments
|Customer's mail client stripped `[ZapDesk #N]` from the subject — check the rendered subject in the customer's reply.

|Confirmations not arriving
|Outbound mail unconfigured, or the sender mailbox is restricted by the Application Access Policy.

|Same email creates two tickets
|Either two pollers ran at once -- check that only one of the Logic App, the
Functions timer and the GitHub Actions workflow is enabled, and that no run
of the old one overlapped the new -- or `mark-as-read` failed after a
successful ingest, for which the server logs carry `failed to mark … read`.
The mailbox can be safely cleaned up; future polls will continue normally.
|===
