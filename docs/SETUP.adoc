== Overview

ZapDesk is a Zendesk-style support ticketing portal that uses Azure DevOps as its backend. Work items tagged with `ticket` are displayed as support tickets.

== Prerequisites

* Azure subscription
* Azure DevOps organization
* Microsoft 365 tenant (for authentication and email)
* GitHub repository (for CI/CD)

== Azure AD App Registration

. Go to https://portal.azure.com[Azure Portal] > Azure Active Directory > App registrations
. Click "New registration"
. Configure:
** Name: `ZapDesk`
** Supported account types: "Accounts in this organizational directory only"
** Redirect URI: `https://zapdesk.yourdomain.com/api/auth/callback/azure-ad` (Web)
. After creation, note the:
** Application (client) ID → `AZURE_AD_CLIENT_ID`
** Directory (tenant) ID → `AZURE_AD_TENANT_ID`
. Go to "Certificates & secrets" > "New client secret"
** Note the secret value → `AZURE_AD_CLIENT_SECRET`
. Go to "API permissions" and add:
** Microsoft Graph: `User.Read`, `email`, `profile`, `openid`
** Azure DevOps: `user_impersonation`

=== Letting other organisations install ZapDesk

One ZapDesk can serve many organisations. Each one's admin installs it with a
button, and their people then sign in with their own Microsoft account and see
their own Azure DevOps. ZapDesk stores nothing about them: the install is a
consent in their tenant, and personal settings stay on each person's profile.

. In the app registration, under *Authentication*, set *Supported account
  types* to "Accounts in any organizational directory (Multitenant)".
. Add a second *Web* redirect URI: `https://zapdesk.yourdomain.com/api/install/callback`.
. Under *API permissions*, the Microsoft Graph *application* permission
  `User.ReadWrite.All` is what the Lightning Address and GitHub username
  features use. Every installing admin is asked to grant the permissions
  listed here.
. Set `AZURE_AD_MULTI_TENANT=true` in the App Service configuration and
  restart. Keep `AZURE_AD_TENANT_ID` set to your own tenant.

An admin of another organisation then opens `/install` (linked from the login
page), clicks *Install for my organisation*, and approves the permissions on
Microsoft's page. They need the Global Administrator, Privileged Role
Administrator or Cloud Application Administrator role. Microsoft then lists
ZapDesk under *Enterprise applications* in their tenant, where they can remove
it again.

* Sign-in uses the `organizations` endpoint, so work and school accounts from
  any tenant that has installed ZapDesk can sign in. Personal Microsoft
  accounts cannot.
* Profile features (Lightning Address, GitHub username) read and write the
  signed-in user's own tenant, with a Graph token from that tenant.
* `AZURE_DEVOPS_ORG` is only a default for server-side work such as email
  ingest. People pick their Azure DevOps organisation in the header.

== Azure DevOps Configuration

=== Personal Access Token (PAT)

Create a PAT for the service account used to create tickets from emails:

. Go to https://dev.azure.com[Azure DevOps] > User Settings > Personal Access Tokens
. Create new token with scopes:
** Work Items: Read & Write
** Project and Team: Read
. Note the token → `AZURE_DEVOPS_PAT`

=== Email Routing

Email routing is configured via Azure DevOps project descriptions. Add an `Email:` line to each project's description to specify which email domains route to that project.

.Example project description
----
Customer support project for Example Ltd.

Email: example.com
SLA: Gold
----

.Multiple domains
----
Example Group customer support portal.

Email: example.com, example.ie
----

The system queries DevOps every 5 minutes to refresh the routing map. There are no built-in domains: a domain that no project lists is not routed. The first domain also shows as the organization's domain in ZapDesk, and the `SLA:` line sets its SLA level (Gold, Silver or Bronze).

== Azure App Service

=== Create App Service

[source,bash]
----
# Create App Service Plan
az appservice plan create \
  --name zapdesk-plan \
  --resource-group KnowAllAIRG \
  --sku B1 \
  --is-linux

# Create Web App
az webapp create \
  --name zapdesk-knowall \
  --resource-group KnowAllAIRG \
  --plan zapdesk-plan \
  --runtime "NODE:20-lts"

# Enable HTTPS only
az webapp update \
  --name zapdesk-knowall \
  --resource-group KnowAllAIRG \
  --https-only true
----

=== Custom Domain

. Add CNAME record: `zapdesk` → `zapdesk-knowall.azurewebsites.net`
. Add custom domain to App Service:
+
[source,bash]
----
az webapp config hostname add \
  --webapp-name zapdesk-knowall \
  --resource-group KnowAllAIRG \
  --hostname zapdesk.yourdomain.com
----

. Create managed SSL certificate (after DNS propagates):
+
[source,bash]
----
# Create certificate
az webapp config ssl create \
  --name zapdesk-knowall \
  --resource-group KnowAllAIRG \
  --hostname zapdesk.yourdomain.com

# Bind certificate (use thumbprint from previous command)
az webapp config ssl bind \
  --name zapdesk-knowall \
  --resource-group KnowAllAIRG \
  --hostname zapdesk.yourdomain.com \
  --certificate-thumbprint <THUMBPRINT> \
  --ssl-type SNI
----

== GitHub Secrets

Configure these secrets in your GitHub repository for the CI/CD pipeline:

[cols="1,2"]
|===
|Secret |Description

|`AZURE_WEBAPP_PUBLISH_PROFILE`
|Azure Web App publish profile (XML). Get with: `az webapp deployment list-publishing-profiles --name zapdesk-knowall --resource-group KnowAllAIRG --xml`

|`NEXTAUTH_SECRET`
|Random 32-byte hex string. Generate with: `openssl rand -hex 32`

|`AZURE_AD_CLIENT_ID`
|Azure AD Application (client) ID

|`AZURE_AD_CLIENT_SECRET`
|Azure AD client secret value

|`AZURE_AD_TENANT_ID`
|Azure AD Directory (tenant) ID

|`AZURE_DEVOPS_PAT`
|Azure DevOps Personal Access Token

|`EMAIL_WEBHOOK_SECRET`
|Secret for validating inbound email webhooks. Generate with: `openssl rand -hex 16`

|`SMTP_PASSWORD`
|SMTP password for outbound emails (Microsoft 365 app password)
|===

.Set secrets via CLI
[source,bash]
----
# Auto-generated secrets
az webapp deployment list-publishing-profiles \
  --name zapdesk-knowall \
  --resource-group KnowAllAIRG \
  --xml | gh secret set AZURE_WEBAPP_PUBLISH_PROFILE

gh secret set NEXTAUTH_SECRET --body "$(openssl rand -hex 32)"
gh secret set EMAIL_WEBHOOK_SECRET --body "$(openssl rand -hex 16)"

# Your credentials
gh secret set AZURE_AD_CLIENT_ID --body "your-client-id"
gh secret set AZURE_AD_CLIENT_SECRET --body "your-client-secret"
gh secret set AZURE_AD_TENANT_ID --body "your-tenant-id"
gh secret set AZURE_DEVOPS_PAT --body "your-devops-pat"
gh secret set SMTP_PASSWORD --body "your-smtp-password"
----

== Email Configuration

=== Inbound Email (Webhook)

Configure your email provider to forward emails to `your-support-email@yourdomain.com` via webhook:

* Webhook URL: `https://zapdesk.yourdomain.com/api/email/webhook`
* Header: `x-webhook-secret: <EMAIL_WEBHOOK_SECRET>`
* Payload format:
+
[source,json]
----
{
  "from": "sender@example.com",
  "subject": "Help needed",
  "body": "<html>...</html>"
}
----

=== Outbound Email (SMTP)

ZapDesk uses Microsoft 365 SMTP for sending emails:

* Host: `smtp.office365.com`
* Port: `587`
* User: `your-support-email@yourdomain.com`
* TLS: Required

Create an app password in Microsoft 365 admin for the SMTP_PASSWORD.

== GitHub Issues

Optional. ZapDesk can show GitHub issues beside Azure DevOps work items in the
tickets list and on the Kanban boards, for projects that track work in GitHub
as well as, or instead of, DevOps. The issues are read-only in ZapDesk: each
row or card links to the issue on GitHub.

There are two ways to set this up; both can be used together.

* *The ZapDesk GitHub App* (below): each DevOps project admin connects their
  own GitHub organisation from the project page. Use this when ZapDesk serves
  more than one organisation.
* *A server token and mapping* (`GITHUB_TOKEN`, `GITHUB_PROJECT_REPOS`): an
  admin of the server lists the repositories. Simplest for one organisation.

=== The ZapDesk GitHub App

Register one GitHub App for this ZapDesk. It serves every organisation that
connects to it.

. On GitHub, under the account that will own the App: *Settings > Developer
  settings > GitHub Apps > New GitHub App*.
. Name it (the URL name becomes `GITHUB_APP_SLUG`), with homepage URL
  `https://zapdesk.yourdomain.com`.
. *Callback URL*: `https://zapdesk.yourdomain.com/api/github/setup`. Tick
  *Request user authorization (OAuth) during installation*. ZapDesk needs the
  code this adds to check that the person connecting can see the installation.
. *Webhook*: active, URL `https://zapdesk.yourdomain.com/api/github/webhook`,
  with a random secret (`GITHUB_APP_WEBHOOK_SECRET`). Optional: without it,
  changes show once the one-minute cache expires.
. *Permissions*: Repository > *Issues*: read-only, *Pull requests*: read-only
  (for the Kanban board's pull request counts), *Metadata*: read-only.
  *Subscribe to events*: *Issues*.
. *Where can this GitHub App be installed?*: *Any account*.
. After creating it, note the *App ID* (`GITHUB_APP_ID`) and *Client ID*
  (`GITHUB_APP_CLIENT_ID`). Generate a client secret
  (`GITHUB_APP_CLIENT_SECRET`) and a private key (`GITHUB_APP_PRIVATE_KEY`,
  the whole PEM file; App Service settings may write its line breaks as `\n`).

Set those values in the App Service configuration and restart. A *GitHub*
card then appears on each project page:

* Someone who can edit the project in Azure DevOps clicks *Connect GitHub*,
  installs the App on their GitHub organisation and picks repositories.
* The link is kept on the DevOps project, as the project property
  `ZapDesk.GitHubInstallation`. ZapDesk has no database, and only people who
  can edit the project can change it.
* Everyone who can see the project sees its issues. Each installation has its
  own GitHub rate limit.
* *Disconnect* removes the link. Uninstalling the App on GitHub stops it
  working too.

=== Token

Create a GitHub token the server uses to read issues, and set it as
`GITHUB_TOKEN` in the App Service configuration.

* A fine-grained personal access token is enough.
* Repository access: only the repositories you will map.
* Permissions: *Issues* and *Pull requests*, read-only. Pull requests feed the
  Kanban board's 24h summary.

The token stays on the server. It is shared by every ZapDesk user, so it has
one rate limit (5,000 requests an hour); ZapDesk reuses each repository's
issues for a minute to stay well inside it.

=== Project to repository mapping

Set `GITHUB_PROJECT_REPOS` to a JSON object of Azure DevOps project name to
the GitHub repositories that belong to it:

[source,json]
----
{
  "Project One": ["your-org/repo-one", "your-org/repo-two"],
  "Project Two": ["your-org/another-repo"]
}
----

* Project names match without regard to case.
* A repository is written as `owner/repo`. Anything else is ignored, with a
  warning in the server log.
* `owner/*` stands for every repository of that GitHub organization that the
  token can read, so repositories do not have to be listed one by one and new
  ones appear by themselves:
+
[source,json]
----
{ "Project One": ["your-org/*"] }
----
+
A repository that is also named for another project stays with that project
only. Up to 1,000 open issues and pull requests are read for an organization;
beyond that, the server log says so and the rest are not shown.
* A user sees a repository's issues only if they can see the DevOps project it
  is mapped to, in the organization they have selected.

Restart the app after changing either value.

=== Linking GitHub accounts to people

Nothing on GitHub says which Azure DevOps user an account belongs to, so
without a link a person appears twice: under their DevOps name and under their
GitHub username. There are two ways to link them.

==== On each person's profile

Each person opens *Profile* and saves their GitHub username in the *GitHub*
card, which appears once GitHub issues are configured. The username is stored
in their Microsoft profile, in the same `zapdesk.knowall.ai` extension as
their Lightning Address, so no admin step is needed when someone joins.

* ZapDesk reads the saved usernames with the app's Microsoft Graph
  *application* permission `User.ReadWrite.All` (admin consent), the one the
  Lightning Address already needs. It reads the users of the signed-in
  person's own tenant: `AZURE_AD_TENANT_ID` for a single-organisation
  ZapDesk, or each installing organisation's tenant when other organisations
  can install it (`AZURE_AD_MULTI_TENANT`). The result is kept for ten
  minutes per tenant; a save on the same server takes effect at once.
* A linked account becomes the Azure DevOps user with the same email address,
  else the one with the same display name, else the profile's name and email.
* A username can be linked to one person only: saving one someone else has
  already linked is refused.
* A username saved in one tenant is only matched to issues for people
  signed in to that tenant. Guests (whose profile lives in another
  directory) and personal Microsoft accounts cannot save a username this way;
  use `GITHUB_USER_MAP` for them. On a multi-tenant ZapDesk, people of an
  organisation that has installed it save theirs in their own tenant.

==== In the server configuration

Set `GITHUB_USER_MAP` to a JSON object of GitHub username to the person's
DevOps display name. An entry here wins over a username saved on a profile:

[source,json]
----
{
  "github-username": "DevOps Display Name",
  "another-username": "Another Person"
}
----

* Usernames and names match without regard to case.
* A mapped person's issues are listed under their DevOps name: in the
  *Assignee* and *Requester* columns, and when the Kanban Board page is grouped
  by person.
* When ZapDesk can read the organization's user list, a mapped person also
  takes their DevOps avatar and identity, so their GitHub issues count as
  theirs in the *Your active tickets* view. Without that permission, only the
  name changes.
* A username that is neither in the mapping nor saved on a profile is shown as
  it is on GitHub.

Restart the app after changing the value.

=== What appears

When GitHub issues are set up, a *Both / DevOps / GitHub* toggle appears in
the top right of the header, and the tickets list gains a *Source* column.
That is either the ZapDesk GitHub App (all five `GITHUB_APP_*` values) or the
server token and mapping (both `GITHUB_TOKEN` and `GITHUB_PROJECT_REPOS`).
With neither, the toggle and column do not appear. With the App, a project's
issues show once someone has connected it on its project page.

On the Kanban boards (the Kanban view of the tickets page, and the Kanban
Board page) an issue is a card marked with the GitHub icon and its
`owner/repo#number`. The columns are Azure DevOps states and an issue is only
open or closed, so open issues sit in the first column and closed ones in
*Closed*. The Kanban view of the tickets page shows active items only, so
closed issues appear on the Kanban Board page alone. An issue card cannot be
dragged. On the Kanban Board page, issues
appear under the project their repository is mapped to; grouped by person,
they appear under the assignee's DevOps name when the account is linked (see
above), and under the GitHub username otherwise.

[cols="1,1"]
|===
|GitHub |ZapDesk

|open / closed
|Status `Open` / `Closed`

|First assignee
|Assignee

|Labels
|Tags

|Author
|Requester
|===

Open issues are listed, plus closed issues updated in the last seven days,
the same window the Kanban Board uses for closed work items. Pull requests are
not listed as tickets, but the Kanban board's 24h summary counts those opened,
updated or merged in its window, under the person (mapped like issue authors)
and the project of the repository. A GitHub pull request lights up the work
items it names as `AB#123` in its title or description.

Not covered yet: the project page and the sidebar counts. The *Your active
tickets* view matches on email address, which GitHub does not expose, so it
lists a person's GitHub issues only when their account is linked: saved on
their profile, or in `GITHUB_USER_MAP` when ZapDesk can also read the
organization's user list.

== Local Development

. Copy `.env.example` to `.env` and fill in values
. Install dependencies: `npm install`
. Run development server: `npm run dev`
. Open http://localhost:3000

== Deployment

The GitHub Actions workflow automatically deploys to Azure on push to `main`:

. Builds the Next.js application
. Uploads artifacts
. Deploys to Azure Web App
. Configures app settings

Manual deployment trigger: Go to Actions > "Deploy to Azure App Service" > "Run workflow"
