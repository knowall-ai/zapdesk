== Overview

This guide covers testing strategies and procedures for ZapDesk.

== Test Types

=== Unit Tests

Unit tests for utility functions and services, run with Vitest. Files are
`src/**/*.test.ts`.

[source,bash]
----
bun run test:unit         # single run
bun run test:unit:watch   # watch mode
----

==== Test environment

`vitest.config.ts` runs on the `node` environment, which is what most utility
tests want and is the faster of the two.

Tests that need a real DOM opt in per file with a docblock on the first line,
rather than switching the whole suite to `jsdom`:

[source,typescript]
----
// @vitest-environment jsdom
----

`src/lib/sanitize-html.test.ts` uses this, because DOMPurify sanitises by
parsing markup into a DOM and walking it — there is nothing to test against
without one. `jsdom` is a dev dependency and is only loaded by files carrying
the docblock.

==== HTML sanitisation coverage

`src/lib/sanitize-html.test.ts` covers the boundary described in
`SOLUTION_DESIGN.adoc` under _Rendering Work Item HTML_, in four groups:

* *Vectors that must not survive* — `<script>`, inline event handlers
  (`onerror`, `onclick`), `javascript:` URLs including control-character
  variants such as `java<TAB>script:`, `vbscript:`, non-image `data:` URLs,
  `<iframe>` and `<form>`.
* *Formatting that must survive* — bold, lists, links, tables with `colspan`,
  `width` and `align`, inline `style`, and the base64 `data:image` URIs the
  DevOps editor pastes. This half is the one that catches over-tightening: an
  earlier `ALLOWED_URI_REGEXP` silently stripped table attributes, and only
  these tests found it.
* *Inline CSS* — that fetching functions, every `position`, the other routes out
  of the box (`z-index`, `transform`, `float`, `inset`, `opacity`, …) and
  negative margins are dropped from a `style` attribute, while the colours,
  fonts, spacing and borders beside them survive. DOMPurify does not read CSS, so this group covers
  code that is entirely ours.
+
NOTE: One case is weaker under `jsdom` than it looks. `sanitizeStyle` defends
against CSS escapes (`u\72 l(…)` resolves to `url(…)` in a browser) by judging
the *parsed* value. A real browser resolves the escape and the function
allowlist then rejects it; `jsdom` rejects the escaped declaration at the parser
and never emits it. Both block the payload, so the assertion holds either way —
but in this environment it proves the output is safe rather than which half
stopped it.
* *Mentions* — that `@mentions` are wrapped in prose, that they are left alone
  inside links and code blocks, and that a mention inside an attribute value is
  no longer rewritten.

When changing the allowlist, add a test to both of the first two groups: one
proving the new vector is blocked, one proving the content you meant to keep
still renders.

=== Integration Tests

Integration tests for API routes.

[source,bash]
----
bun run test:integration
----

=== End-to-End Tests

Playwright tests for full user flows.

[source,bash]
----
bun run test:e2e
----

== Running Tests

=== Prerequisites

1. Install dependencies:
[source,bash]
----
bun install
----

2. Install Playwright browsers:
[source,bash]
----
bunx playwright install
----

3. Set up test environment:
[source,bash]
----
cp .env.example .env.test
----

=== Run All Tests

[source,bash]
----
bun run test
----

=== Run Specific Tests

[source,bash]
----
# Unit tests only
bun run test:unit

# Integration tests only
bun run test:integration

# E2E tests only
bun run test:e2e

# Specific test file
bunx playwright test tests/tickets.spec.ts
----

== Manual Testing Checklist

=== Authentication

* [ ] Sign in with Microsoft account
* [ ] Verify redirect to home page after login
* [ ] Verify user name displayed in header
* [ ] Sign out successfully
* [ ] Verify redirect to login page when accessing protected route

=== Ticket List

* [ ] View all unsolved tickets
* [ ] Filter by "Your unsolved tickets"
* [ ] Filter by "Pending tickets"
* [ ] Filter by "Unassigned tickets"
* [ ] Sort by status, date, priority
* [ ] Search tickets
* [ ] Verify only "ticket" tagged items appear

=== Ticket Detail

* [ ] View ticket details
* [ ] See ticket description/content
* [ ] View comments
* [ ] Add public comment
* [ ] Add internal note
* [ ] View ticket in Azure DevOps (external link)
* [ ] See requester information
* [ ] See assignee information

=== Organizations

* [ ] View list of organizations
* [ ] Search organizations
* [ ] See organization details (domain, tags)
* [ ] Click through to organization detail

=== Customers

* [ ] View list of customers
* [ ] Search customers
* [ ] See customer details (email, timezone)
* [ ] View customer ticket history

=== Dashboard

* [ ] View ticket statistics
* [ ] Verify stat counts match filters
* [ ] Quick action links work
* [ ] Project links work

== Test Data Setup

=== Azure DevOps Test Items

Create test work items in Azure DevOps:

1. Create Task work item
2. Add "ticket" tag
3. Set various states (New, Active, Resolved)
4. Set different priorities
5. Add comments

=== Test Scenarios

==== Scenario 1: New Ticket

1. Create Task in DevOps
2. Add "ticket" tag
3. Verify appears in ZapDesk
4. Check status shows as "New"

==== Scenario 2: In Progress Ticket

1. Change DevOps state to "Active"
2. Verify ZapDesk shows "Open"
3. Change to "Doing"
4. Verify shows "In Progress"

==== Scenario 3: Add Comment

1. Open ticket in ZapDesk
2. Add comment
3. Verify comment appears
4. Check comment visible in DevOps

== Playwright Test Structure

=== Test Files

[source]
----
tests/
├── auth.spec.ts        # Authentication tests
├── tickets.spec.ts     # Ticket listing tests
├── ticket-detail.spec.ts # Ticket detail tests
├── organizations.spec.ts # Organization tests
├── customers.spec.ts   # Customer tests

    └── test-data.ts    # Test data helpers
----

=== Example Test

[source,typescript]
----
import { test, expect } from '@playwright/test';

test.describe('Ticket List', () => {
  test.beforeEach(async ({ page }) => {
    // Login before each test
    await page.goto('/login');
    // ... login flow
  });

  test('should display tickets', async ({ page }) => {
    await page.goto('/tickets');
    await expect(page.locator('h1')).toContainText('unsolved tickets');
    await expect(page.locator('table')).toBeVisible();
  });

  test('should filter pending tickets', async ({ page }) => {
    await page.goto('/tickets?view=pending');
    await expect(page.locator('h1')).toContainText('Pending tickets');
  });
});
----
